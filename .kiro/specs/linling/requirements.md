# Requirements — linling（对话智能体平台）

> 项目名 `linling`。
> 本 spec 旨在把 QRDic（QRSpeed 脚本机器人）重写为一个**跨平台、可插件化、面向非程序员 DIY** 的对话智能体框架。

## 1. 背景

老项目 `QRDic/dicpro.txt` 是一个 10k 行的 Android QRSpeed DSL 脚本，实现了"涂山苏苏"QQ 群机器人：签到、灵玉、扭蛋、钓鱼、21点、卧底、偷玉、路线、AI 对话等。它的价值不在代码，而在**规则集**（业务设计）和**DSL 思路**（让非程序员用中文写机器人）。

但它也有明显痛点：
- 运行时强绑 Android + QRSpeed，无法迁移到服务器或其他 IM；
- 数据层用平铺 Properties 文件，并发、索引、迁移能力弱；
- LLM 能力是硬编码的 HTTP 调用，没有记忆 / 工具 / 多轮；
- DSL 没有正式语法，写多了就是玄学调试。

## 2. 项目目标

做一个**标准的多平台对话智能体平台**，同时覆盖两类使用者：

- **DIY 玩家**（原 QRDic 受众）：不写代码，用中文规则脚本配出自己的群机器人。
- **Agent 开发者**：用 Python/TS 注册工具、编排 Agent、接入 LLM。

关键词：
- **LLM 部分 = Agent 框架**（标准化：工具调用、记忆、人设、多提供方）
- **指令触发部分 = DSL 解释器**（正式语法，向后兼容 QRDic 风格）
- **平台接入 = 适配器插件**（QQ 先行，留好微信 / 飞书 / Discord / Slack / HTTP / CLI 的位置）
- **DSL 与 Agent 共享工具注册表**（中文关键字函数 ↔ Python/TS 函数 ↔ LLM tool 同源）

## 3. 非目标（明确不做）

- 不做 Android 端运行时；服务端部署为主。
- 不自研 LLM；只做编排与调用。
- 不做 QQ 协议端；复用 OneBot（NapCat / Lagrange / gocq 等任一实现）。
- 不兼容 QRSpeed 的每一个偏门语法（例如某些 undocumented 隐式行为），只兼容成熟且有真实用例的那些。

## 4. 用户角色

| 角色 | 描述 |
|---|---|
| 运维 Admin | 部署实例、配置 LLM key / 平台凭证 / 存储。 |
| 机器人作者 | 写规则脚本或 Python 插件、定义人设、注册工具。 |
| 终端用户 | 在 QQ 群/私聊里和机器人互动。 |
| 插件开发者 | 为平台写适配器、工具、存储后端。 |

## 5. 用户故事（EARS 风格）

### 5.1 平台适配
- US-P1. **作为 Admin**，我希望通过一份配置接入 OneBot，使机器人能收发 QQ 群/私聊消息。
- US-P2. **作为插件开发者**，我希望实现一个 `PlatformAdapter` 接口就能新增一个平台（微信/飞书/Discord/CLI/HTTP Webhook），**不改内核**。
- US-P3. **系统**应把不同平台的消息规范化为统一 `Event` 模型（文本、图片、@、回复、戳一戳、文件等），对上层透明。
- US-P4. **系统**在发送时应把统一的 `Action` 反向映射到各平台能力；平台不支持的能力应降级并记录告警。

### 5.2 DSL 解释器
- US-D1. **作为机器人作者**，我希望用纯中文写规则（触发器 + 条件 + 读写 KV + 模板输出），不写任何 Python。
- US-D2. **当** 用户消息匹配触发器正则，**系统**应执行对应规则体；匹配按优先级或首匹配（可配置）。
- US-D3. **系统**应支持 `如果/如果尾`、`正则:`、`返回`、`:label` / `$jump$`、`[内部]` 私有处理器、`$调用 毫秒 处理器$` 延时调度、`$回调$` 同步调用、局部变量赋值 `名:值`、算术表达式 `[...]`、模板占位 `%名%`、函数调用 `$名 参数...$`。
- US-D4. **系统**必须拒绝语法错误的规则并**指向出错行号**，不能像老 DSL 一样静默吞错。
- US-D5. **作为 Admin**，我希望脚本运行在沙箱里：不能写任意磁盘路径、不能发任意 HTTP、不能在循环里卡死进程。
- US-D6. **系统**应能一次性导入老 QRDic `dicpro.txt` + `data/**`，并尽量跑起来；不兼容的语法给出迁移报告。

### 5.3 Agent 框架
- US-A1. **作为机器人作者**，我希望用一个 YAML 文件就能定义一个 Agent：LLM 提供方、系统提示、人设、工具、记忆策略。
- US-A2. **系统**应支持多 LLM 提供方（OpenAI / Anthropic / Gemini / 本地 OpenAI 兼容端点），可按 Agent 单独选。
- US-A3. **系统**应支持工具调用（function calling）：工具可用 Python 装饰器注册，也可以直接把 DSL 处理器暴露成工具。
- US-A4. **系统**应提供短期会话记忆（滚动窗口）和可选的长期记忆（向量库）；记忆按 `user × scope` 隔离。
- US-A5. **作为终端用户**，我希望触发一次 Agent 交互时，LLM 的工具调用轨迹可以被 Admin 审计（但不默认暴露给终端用户）。
- US-A6. **系统**应实现安全栏（content policy 钩子、最大 token、超时、最大工具调用链长度）。

### 5.4 DSL ↔ Agent 混合
- US-M1. **作为机器人作者**，我希望 DSL 里能 `$agent 调用 <agent名> <输入>$`，在中文脚本里嵌入 LLM 能力。
- US-M2. **反过来**，我希望 Agent 的工具列表里能直接列出若干 DSL 处理器（例如"查看背包"），Agent 可以选择性调用。
- US-M3. **系统**必须有一个**共用工具注册表**：同一个工具同时有 DSL 名、Python 名、LLM schema 三种视图，同一份实现。

### 5.5 存储与数据
- US-S1. **系统**应提供 KV 存储抽象（`scope/namespace/key → value`），对应老 DSL 的 `$读$ / $写$`；默认实现支持 SQLite/Postgres/Redis。
- US-S2. **系统**应提供结构化存储（SQL 表）给 Python 插件使用。
- US-S3. **系统**应提供文件存储（图片、音频等）。
- US-S4. **系统**应提供导入工具，把老 `QRDic/data/**` 的 Properties 文件迁成 KV 行；**带回滚**（保留 `.bak` 的方式）。

### 5.6 调度与时间
- US-T1. **系统**应支持一次性延时任务（对应 `$调用 ms handler$`）。
- US-T2. **系统**应支持 cron/间隔定时任务（原 DSL 没有，属于增强）。
- US-T3. **系统**应在进程重启后恢复"尚未触发的延时任务"，任务持久化。

### 5.7 管理与可观测
- US-O1. **Admin** 应能通过 Web UI 或 CLI 查看：收到的事件、触发的处理器、LLM 调用、工具调用、错误。
- US-O2. **系统**应输出结构化日志与指标（每分钟事件数、LLM token 用量、规则耗时 top）。
- US-O3. **Admin** 应能热加载规则脚本和 Agent 配置，不重启进程。

### 5.8 多租户与安全
- US-X1. **系统**应支持多实例（多机器人账号、多群/多工作区）隔离存储与规则。
- US-X2. **系统**应支持权限：全局管理员、群管、普通用户；DSL 条件可引用 `%角色%`。
- US-X3. **系统**应在存储层加密或脱敏敏感字段（LLM key、平台凭证）。
- US-X4. **来自外部 API 的内容**（HTTP 返回、文件内容、用户消息）对规则和 Agent 均为不可信输入，禁止直接注入为 prompt / 指令控制字段。

### 5.9 非功能需求
- NFR-1. **语言/运行时**：Python 3.11+（也可 TS/Node，二选一，本 spec 默认 Python）。
- NFR-2. **部署**：单容器即能跑起来；可选 Postgres + Redis + 对象存储。
- NFR-3. **并发**：基于 asyncio；处理单条消息应为非阻塞。
- NFR-4. **延迟**：不走 LLM 的规则路径，端到端 p95 < 200 ms（不含网络往返）。
- NFR-5. **测试**：核心解释器单测覆盖率 ≥ 80%；适配器集成测试用 mock 平台。
- NFR-6. **文档**：DSL 语法表、工具注册表、每个适配器的映射矩阵都要有中文文档。

## 6. 迁移/兼容性需求

- MIG-1. 能读 `QRDic/dicpro.txt` 并生成 AST；无法识别的段落生成"迁移 TODO 报告"。
- MIG-2. 能读 `QRDic/data/**` 的 Java Properties 文件，写入新 KV 存储；路径约定：`data/<a>/<b>/<file>` → `scope="<a>/<b>"`, `key="<file>:<原始键>"`（具体 key 方案在 design.md 里）。
- MIG-3. `$BSH 图文.java imagettftext ...$` 这类外挂应替换为 Python 实现（Pillow + 中文字体），**函数签名保持**，DSL 不用改。
- MIG-4. 所有硬编码的 QQ 号（例如作者号 `2078123478`、主群 `754800438`）迁移到配置，规则里用 `%管理员%` `%主群%` 占位。

## 7. 成功判据

- S-1. 能在服务器上以单个 Docker 容器跑起来，挂 QQ 群机器人。
- S-2. 老 `dicpro.txt` 的"打卡 / 灵玉 / 扭蛋 / 钓鱼 / 查看背包 / 戳一戳"六条主路径**原样脚本迁移**即可工作。
- S-3. 可以新建一个 YAML 定义的 Agent，和 DSL 处理器共用同一个"查看背包"工具。
- S-4. 可以新增一个 CLI 适配器，在终端里复现群里聊天的行为用来做离线调试。
- S-5. DSL 有正式 EBNF 语法定义，并由生成器驱动文档。

## 8. 风险与开放问题

- R-1. QRSpeed DSL 有许多 undocumented 行为（`%参数-1%` 是否等价 `%参数1..n%` 拼接？`正则:` 的转义规则？），以老代码实测为准，用迁移测试集固化。
- R-2. OneBot 不同实现对"戳一戳 / 转发 / 卡片消息"支持程度不一，适配层要能优雅降级。
- R-3. LLM 对长系统提示 + 工具集的响应延迟；按 Agent 粒度允许流式响应。
- R-4. DIY 用户可能写出死循环或刷屏，沙箱和速率限制必须默认打开。
- R-5. 第三方图 API（`xiaobai.klizi.cn` 等）稳定性差，抽象成 provider 便于替换或移除。
